# Understanding Intersection

This guide explains the project from the outside in: what you are looking at, where its behaviour comes from, and which files you would change to improve it. Paths are relative to the project root unless a section says otherwise. It describes the source in this checkout, rather than a proposed future architecture.

## 1. What this project is and what it does

Intersection is an interactive traffic simulation built for the Jigjoy October 2026 hackathon by students at the University of Novi Sad, Faculty of Technical Sciences.

You watch vehicles approach a four-way junction, stop at signals, cross, and leave. You can choose traffic scenarios, pause or reset a run, change its speed, and inject events such as an ambulance or a demand surge. Panels explain the signal state, traffic measurements, AI activity, and the history of decisions.

The central experiment is comparing two ways to control traffic lights:

- **Traditional control:** lights follow a fixed timing cycle.
- **AI control:** two agents propose plans. Agent A focuses on North/South traffic; Agent B focuses on East/West. When their plans compete, JEV can choose between them or defer. Deterministic code checks and applies the resulting request.

The AI does not directly set lamps. A signal controller enforces the allowed sequence of green, yellow, and all-red phases, including waiting for vehicles to clear the junction. An accepted proposal means the controller accepted a service request; the requested green may start later.

The simulation uses simplified straight-through lanes. It is useful for demonstrating coordination, observing queues, and experimenting with control policies. Its results describe this model; they do not prove that a controller is suitable for a real road.

### Three distinctions that make the code much easier to understand

**Traditional versus AI is a choice of controller.** Both can be shown in the browser and run against the backend.

**Offline versus backend is a choice of where the simulation runs.** The offline demo runs a local browser implementation. The backend runs a separate Node implementation and sends updates to the browser.

**Mock versus live is a choice of how AI results are produced.** A backend session can use mock proposal agents and mock JEV without credentials. Connecting to the backend does not automatically mean live AI. The browser's offline AI activity is simulated.

For example, you can run an AI-controlled session through the backend, with real server physics and mock AI answers. That exercises the coordination plumbing without paying for model calls.

## 2. The overall structure

The repository is an npm workspace: several related packages share one installation and lockfile.

```text
Intersection/
├── apps/
│   ├── web/               Browser application, 3D scene, offline demo
│   └── server/            HTTP/WebSocket server, simulation, AI integration
├── packages/
│   └── shared/            Data definitions and defaults used by both apps
├── docs/                  Guides, contracts, and JSON examples
├── vendor/                Packaged JEV adapter dependency and provenance
├── package.json           Commands for the whole repository
├── package-lock.json      Exact dependency resolution
└── vitest.config.ts       Runs tests across the three workspaces
```

Think of these three packages as responsibilities:

| Package | Main question it answers |
| --- | --- |
| `@intersection/shared` | What does a session, vehicle, proposal, or message look like? |
| `@intersection/server` | What actually happens in a backend simulation? |
| `@intersection/web` | How does a person start, watch, control, and understand a run? |

### Other root directories

| Directory | Contents and purpose |
| --- | --- |
| `.git/` | Git's history and internal repository data. Use Git commands rather than editing it. |
| `.agents/skills/` | Instructions and supporting resources for coding assistants: frontend design, interface work, and TypeSafe integration. These are development aids, not application code. |
| `.claude/` | Claude-specific local settings, agent definitions, and skill resources. |
| `.codex/` | Codex configuration, including hooks. |
| `.impeccable/` | Local configuration and cache for interface design tooling. |

Builds also produce `dist/` directories inside packages. These contain compiled output. TypeScript can create build-information files, and browser tests can create reports and test-result folders. Treat those as generated artifacts; make behavioural changes in source files.

## 3. A small vocabulary for reading the code

| Term | Meaning here |
| --- | --- |
| `.ts` | A TypeScript file: JavaScript with checked descriptions of data and function arguments. |
| `.tsx` | TypeScript that can also describe React interface elements. |
| Component | A reusable piece of the interface, such as an agent card or chart. |
| Hook | A React function that connects a component to state, timing, or browser behaviour. |
| Store | An object holding current state and notifying subscribers when it changes. |
| Schema | A runtime rule describing valid data. This project uses Zod to check incoming JSON, not just TypeScript's compile-time checks. |
| Transport | The interface through which the frontend talks to a simulation, either locally or over the network. |
| Snapshot | A complete description of the current simulation state. |
| Event | A message saying something happened, such as a proposal arriving or a signal changing. |
| Session | One simulation run and its configuration, state, and history. |
| Generation | A counter identifying the current reset of a session. Old responses from before a reset must not affect the new run. |
| Sequence | An ordering number for events. Missing numbers tell the browser it may have missed updates. |
| Correlation/cycle ID | An identifier connecting the two proposals, arbitration, and outcome of one decision round. |
| Seed | The input used to generate repeatable pseudo-random traffic. |
| Provenance | Whether an output came from a mock, a live model, or deterministic code. |
| FSM | Finite state machine: code that allows only particular state transitions, used here for signals. |
| Inference | Asking a model to produce an answer. |
| Arbitration | Choosing between competing proposals, including the option to defer. |

The frontend uses `@/` as shorthand for `apps/web/src/`. Imports from `@intersection/shared` refer to the shared workspace. Server imports ending in `.js` can point to TypeScript source during development because the compiled files will be JavaScript.

## 4. Follow one run through the system

### Starting a backend session

1. `main.tsx` mounts the React app. `App.tsx` supplies application services and routing.
2. `AppShell.tsx` keeps the shared scene mounted while the user moves between pages. It starts resolving the data source in the background.
3. `HomePage.tsx` lets the user choose a mode. `SimulationPage.tsx` assembles the operating screen for the selected mode and scenario.
4. `useSessionLifecycle.ts` opens the session and starts it after the camera's arrival transition.
5. `SessionController.ts` asks the selected transport to create a session.
6. `WebSocketIntersectionTransport.ts` uses HTTP to create it. On the server, `app.ts` validates the request and `sessions.ts` creates a `Simulation`.
7. The server attaches AI coordination if the session uses AI control. It returns a snapshot, and the browser connects to `/ws` for continuing updates.
8. `session.ts` applies snapshots and events to the frontend store. Panels read that store. The scene receives snapshots through an interpolator so cars move smoothly between network updates.

### Pressing Pause

`ControlBar.tsx` calls `SessionController.control("pause")`. The controller creates a request ID and includes the current generation. The transport sends the request to the server. `app.ts` validates it; `Simulation.control()` changes session state; the response updates the browser.

Request IDs protect against applying the same command twice. Generations protect against applying commands to the wrong reset of a run. These solve different problems.

### Running offline

The same interface calls `MockIntersectionTransport.ts`. That creates a browser `MockSimulation`, advanced by `MockDriver`. Its synthetic AI coordinator produces events shaped like backend events. The rest of the interface can consume them through the same contract.

There are therefore **two physics engines and two coordination implementations**. They share data definitions, but changes to the backend engine do not automatically update the browser engine.

### Defaults worth knowing

The current defaults are 8 seconds minimum green, 45 seconds maximum green, 3 seconds yellow, 2 seconds all-red, and 30 seconds fixed green. Confidence thresholds are 0.85 for high confidence and 0.6 for medium confidence.

The scenario catalogue contains normal traffic, rush hour, reverse rush, sudden surge, ambulance priority, competing priorities, simultaneous proposals, JEV uncertainty, and JEV failure. Some demonstrations are explicitly marked mock-only: their scripted model behaviour cannot be promised for a live model.

A new scenario belongs here first. However, the API currently expects exactly nine catalogue entries, so adding a tenth also requires changing that validation and relevant tests.

## 6. Server: the simulation and AI integration

All paths in this section start at `apps/server/`.

### Startup, requests, and session ownership

| File | What it does |
| --- | --- |
| `src/index.ts` | Executable entry point. Loads environment configuration, constructs the AI service and Fastify app, attaches AI to sessions, listens on the configured host/port, and handles shutdown signals. |
| `src/app.ts` | Builds the Fastify application. Registers HTTP endpoints and WebSockets, validates inputs, formats errors, enforces request/socket limits, and starts simulation/snapshot timers. Kept separate from startup so tests can construct it directly. |
| `src/sessions.ts` | Owns the in-memory session map. Creates sessions, tracks elapsed time, advances running simulations, broadcasts queued events, remembers request receipts for duplicate-command protection, and disposes resources. Also defines API error helpers and prevents writes to comparison sessions. |
| `src/comparisons.ts` | Creates independent traditional and AI sessions with matched inputs, runs the comparison, and reports results. Supports reproducible accelerated mock execution and wall-paced live execution. |

There is no database behind these maps. Sessions and receipts disappear when the process restarts. Sessions are retained up to a limit; the default is 32. A comparison consumes two session slots. Closing the browser connection is not the same as deleting its server session.

The normal server loop checks elapsed time every 25 ms and advances physics in 100 ms simulation steps. Snapshots are broadcast every 200 ms; metrics are normally sampled every simulation second. Increasing speed means advancing more simulated time per real second.

### The simulation engine

| File | What it does |
| --- | --- |
| `src/simulation/engine.ts` | Implements the `Simulation` class: vehicles, arrivals, queues, scheduled events, injected effects, signals, metrics, snapshots, and event history. This is the main file for backend traffic behaviour. |
| `src/simulation/rng.ts` | Creates seeded random streams. Different concerns draw from separate streams so an extra random choice in one concern does not unexpectedly change traffic demand. Includes uniform and Poisson draws. |

`engine.ts` is large because it owns several connected systems. Read it by responsibility rather than trying to absorb every line at once:

| Area / methods | What to look for |
| --- | --- |
| Constructor and options | How scenario parameters, seed, timing, and initial state enter the simulation. |
| `control()`, `inject()`, `advance()` | Public operations: start/pause/reset, schedule an event, and move time forward. |
| `step()` | The order of one 100 ms physics update. |
| `expireEffects()`, `applyScheduled()`, `applyInjection()`, `hazards()` | Starting and ending temporary conditions and scheduled/random events. |
| `arrivals()`, `request()`, `spawn()` | Generating demand, retaining arrivals upstream when necessary, and placing vehicles on a lane. |
| `moveLane()`, `despawn()` | Vehicle acceleration, spacing, movement, and completion. |
| `requestGreen()`, `updateSignal()`, `endGreen()`, `changePhase()` | Receiving a service request and enforcing legal signal transitions. |
| `boxOccupied()`, `occupiedIds()` | Checking whether vehicles still occupy the intersection. |
| `observe()` | Summarising a movement group's traffic for AI decisions. |
| `buildMetrics()`, `recordSample()` | Turning internal vehicle/counter state into measurements. |
| `buildSnapshot()`, `checkpointEvent()`, `eventHistory()`, `drain()` | Publishing state, restoring a subscriber's baseline, and delivering events. |

One step expires old effects, applies scheduled inputs, handles hazards and arrivals, updates signals, moves vehicles, removes finished vehicles, admits waiting arrivals, tracks queues, and notifies adaptive coordination. At the run horizon it completes the session and emits final metrics.

The signal sequence is conceptually:

```text
NS green → NS yellow → all red → EW green → EW yellow → all red → …
```

All-red can be held beyond its minimum when the intersection remains occupied. The AI can request service, but the engine owns this sequence.

### AI files

| File | What it does |
| --- | --- |
| `src/ai/config.ts` | Reads mock/live modes, each agent's provider and model, and the mock JEV fixture. Checks model selection against Mozaik's installed registry and reports missing credentials. Also sets timeouts and inference capacity. |
| `src/ai/schemas.ts` | Defines the smaller observation/proposal shapes used at the model boundary. Freezes observations so a decision round has a stable input. Contains JEV's arbitration instructions. |
| `src/ai/service.ts` | Connects Mozaik agent loops and the JEV adapter to application code. Launches two proposal agents concurrently, selects mock/live runners, contains provider failures, tracks global inference capacity, and attaches a coordinator to each AI session. Contains the proposal-agent instruction and provider-specific structured-output schema. |
| `src/ai/coordinator.ts` | Manages one session's decision rounds. Collects and validates proposals, recognises agreement, requests arbitration when needed, applies confidence/freshness rules, sends accepted plans to the engine, and chooses deterministic fallback when necessary. Publishes the events used by the UI. |
| `src/ai/cloud.ts` | Configures optional Mozaik cloud telemetry and condenses repetitive SDK logs into startup status. Cloud streaming is opt-in and separate from model credentials. |

Read `service.ts` for **how models are called** and `coordinator.ts` for **how their answers influence a session**.

A typical round takes one frozen observation, starts both agents, collects their proposals, and checks whether they effectively agree. Competing proposals go through the JEV bridge. Its possible choices are `GRANT_A`, `GRANT_B`, and `DEFER`. The coordinator then checks whether the result is still current and suitable before requesting a green from the engine.

“Still current” involves session identity, generation, cycle identity, decision revision, deadlines, and traffic checks. Physics continues while a live model thinks. A response can be valid JSON yet too old to act on.

On failure, deterministic fallback prioritises responding emergency demand, then waiting/fairness information, and asks the same signal controller for service. Fallback is observable in events; it is not silently labelled as a live AI decision.

Simulation time and rendering time serve different purposes. Physics advances in steps; the display redraws more frequently. Interpolation fills the visual gap between known positions. It changes how movement looks, not the backend's vehicle positions or metrics.

This distinction helps with debugging: if a car looks wrong but snapshots are correct, inspect interpolation and rendering. If the vehicle is wrong in snapshots too, inspect the selected simulation engine.

## 13. Reading measurements and comparisons correctly

A queue is stopped traffic on the simulated approach. Upstream backlog is demand that has been requested but has not yet been admitted to the lane. Looking only at visible cars can hide demand waiting outside the rendered road.

Completed-vehicle averages describe vehicles that have already finished. Active waiting and upstream waiting describe unfinished demand. A controller can appear good on completed averages while leaving a queue behind, so read these together.

A paired comparison creates two independent sessions with matched seed, scenario parameters, and horizon. The current server input hash is SHA-256 of `JSON.stringify({ engine: "sfc32-idm-strict-v1", seed, scenario: parameters })`, in that key order. It identifies immutable inputs, not a hash of either run's changing world state.

Accelerated mock comparisons wait for decision work between physics steps so mock execution can be repeatable. Live comparisons run with wall-clock timing; model answers and latency make them non-repeatable. Matching inputs does not guarantee identical decisions or equal outcomes.

## 14. Where to change things

These are starting points for your own improvements, not claims that every item needs changing.

| What you want to improve | Start here | Also consider |
| --- | --- | --- |
| Traffic demand or a new scenario | `packages/shared/src/contracts/defaults.ts` | Domain/API validation, catalogue count, scenario controls, and tests. |
| Signal timing defaults | Shared `contracts/defaults.ts` | Both engines, UI countdowns, and timing assumptions in tests. |
| Vehicle movement or queue behaviour | Server `simulation/engine.ts` | Browser `transport/mock/engine.ts` if offline behaviour should match. |
| AI prompt or observation | Server `ai/service.ts` and `ai/schemas.ts` | Structured-output validation and what the UI can explain. |
| JEV's decision question | Server `ai/schemas.ts` | Arbitration fixtures and coordinator confidence policy. |
| Confidence, stale-result, or fallback policy | Server `ai/coordinator.ts` | Coordination/safety tests and the offline `mock/adaptive.ts`. |
| Add a different live provider | Server `ai/config.ts` and `ai/service.ts` | Mozaik registry support, keys, structured output, and provider-status presentation. |
| Metrics definition | Engine `buildMetrics()` and shared `schemas/session.ts` | Offline metrics, charts, examples, and comparison interpretation. |
| Decision explanations | `state/transcript.ts`, `jevState.ts`, decision components | Preserve the difference between proposal, accepted request, and actual phase change. |
| Car appearance or road styling | Scene `Vehicles.tsx`, `Diorama.tsx`, `geometry.ts`, `sceneTheme.ts` | Shared physical geometry if dimensions change. |
| Jumpy animation | Scene `interpolation.ts` and transport/snapshot timing | Determine first whether snapshots themselves are discontinuous. |
| Layout or visual hierarchy | `SimulationPage.tsx`, feature components, `index.css` | Smaller screens, reduced motion, and the WebGL fallback. |
| Reconnection problems | Backend transport, `SessionController.ts`, `session.ts` | Event sequences, checkpoints, retained history, and generation changes. |
| Long-running/shared server use | Server `sessions.ts` and `app.ts` | Session cleanup, persistence, ownership, and resource limits. Current storage is in memory. |

Two architectural areas deserve particular attention as the project grows. First, the duplicated engines/coordinators can drift: a feature may work offline and behave differently on the backend. Second, the large engine files combine physics, signal logic, metrics, and event publication. Extracting clear responsibilities could make them easier to change, provided the existing behaviour stays covered.

Before changing a metric or policy, write down the outcome you want in ordinary terms: for example, “reduce the longest wait during an East/West surge without delaying an ambulance.” Then choose scenarios and measurements that can actually show that outcome.

## 15. Running and checking the project

From the repository root, with Node 22 or newer:

```sh
npm ci
npm run build
npm run dev:server
```

In another terminal:

```sh
npm run dev:web
```

Open Vite's printed URL. Choose the data source in Settings. The server normally listens on `127.0.0.1:3001`; traditional and default mock-AI operation require no model keys. For live AI, follow [QUICKSTART.md](QUICKSTART.md) and `apps/server/.env.example`.

| Command | What it checks/does |
| --- | --- |
| `npm run build` | Compiles shared, server, and frontend packages. |
| `npm run typecheck` | Builds shared definitions and checks server/frontend TypeScript. |
| `npm run lint` | Runs Oxlint across the repository. |
| `npm test` | Runs the workspace unit/component suites. |
| `npm run test:e2e -w @intersection/web` | Runs frontend browser journeys. |
| `npm run test:e2e:backend` | Builds and runs browser/backend integration tests. |
| `npm run models -w @intersection/server` | Lists installed supported models. |
| `npm run test:live -w @intersection/server` | Runs the opt-in live smoke script with configured credentials. |

Playwright browser tests require its Chromium installation; the README includes the installation command. These commands describe available verification, not checks performed just by writing this guide.

For a first source-reading pass, follow this order: shared defaults → `SimulationPage.tsx` → `useSessionLifecycle.ts` → `SessionController.ts` → backend `app.ts` → engine `step()` → `coordinator.ts` → `service.ts`. That follows the path from a person's choice to traffic movement and AI decisions.
